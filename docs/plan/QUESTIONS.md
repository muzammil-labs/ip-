## Phase 3

- **UI-3.6 MSW's browser worker chunk is on the critical path in every environment, and it is large (~97KB gzip).** The task is explicit: "Start the worker in main.tsx before rendering (all environments, since there is no real backend yet)," so `main.tsx` awaits `worker.start()` before the first `render()` call. Vite still code-splits `src/api/mock/browser.ts` into its own chunk (dynamic `import()`), so the main entry chunk itself stays well under the Part E 200KB budget (168.85KB gzip after UI-3.1's route-level code-splitting), but the mock worker chunk still has to download, parse and register before the user sees anything, which real users of the eventual production build (once a real backend exists and MSW is removed) will never pay. Worth re-measuring actual time-to-first-render once Lighthouse is wired up in Phase 7, and considering whether MSW should be gated behind an env check (`import.meta.env.DEV` or a build flag) rather than always-on, if the demo's real backend lands before finals. For now this matches the task's literal instruction.
- **UI-3.1 Router: most Case chapters and pages are still placeholders or reused old screens, not full rebuilds.** `chapters/Classify.tsx`, `Say.tsx` and `Search.tsx` re-export the pre-redesign `Classify`, `ClaimCheck` and `PriorArt` screens as-is (they already have their own headers, so they are not wrapped in the `Chapter` primitive, to avoid a double header). `chapters/Describe.tsx`, `Protect.tsx`, `Owe.tsx` and `Dossier.tsx` are genuinely new chapters with no prior content, so they use the `Chapter` primitive with an `EmptyState` placeholder rather than inventing chapter content the plan hasn't specified. Similarly `pages/Home.tsx`, `Library.tsx` and `HowItWorks.tsx` re-export `Overview`, `Sources`, and `Trust`+`Blueprint` stacked. All of this is explicitly Phase 4 work ("Rebuild every page on the system"); UI-3.1's job was the routing infrastructure itself, which is real and fully working (hash routes, lazy loading, browser back/forward, scroll-to-top on route change only). `pages/DossierPrint.tsx` and `Facilitator.tsx` are also EmptyState placeholders pending their respective engines (Phase 6).
- **UI-3.1 old screens' internal cross-navigation buttons now route through `lib/legacyRoutes.ts`'s `SCREEN_ROUTE` map** (old `Screen` key to real B2 hash path) instead of the retired `useApp().go()`, since nothing renders based on the old `screen` state anymore. `store.tsx` still carries `screen`/`go` (harmless, unused for routing) since several Case-related fields share the same reducer; safe to remove once Phase 4 finishes retiring the old screens.
- **UI-3.4 share link uses a native `window.confirm()` for the "load a different case?" prompt**, per the task's literal wording ("after a confirm dialog"). Confirmed correct behavior with `decodeSharedCase`/`encodeCaseForShare`/`shareLinkFor` unit tests (`tests/lib/shareLink.test.ts`) and a real browser round-trip (generate the link, open it, decode). Worth swapping for a proper Radix AlertDialog once UI-2.17's Sheet/Dialog primitives are wired into a chapter, both for a nicer look and for reliable e2e testability; not blocking since the underlying logic is unit-tested and the current UX is functional.
