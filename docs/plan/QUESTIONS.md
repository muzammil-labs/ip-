- **UI-6.2's `versionAt` had a real off-by-fallback bug caught by manual verification, not by the unit tests written first.** The initial implementation fell back to a source's *last* version whenever `asOf` fell outside every version's window, on the (wrong) assumption that the only way to miss every window is a date after history ends. In fact a date *before* the first version's start also misses every window (windows are `[from, to)`, and the first version's `from` isn't 1 January of year zero), and in that case the old code returned the *most recent* status for a date that predates the *earliest* status. Caught by manually dragging the Legal time machine slider on `#/library/dr-170` to 1 January 2018 (a month before Rule 170's own recorded insertion) and seeing "Omitted" (2025's status) instead of "In force" (Rule 170's actual 2018 status before its own insertion date even applies, the nearest sensible answer). Fixed by comparing `asOf` against `versions[0].from` to pick first-vs-last, with a regression test added (`tests/engines/asOf.test.ts`, "falls back to the first version, not the last..."). Worth remembering for UI-6.3 and any other engine with date-range fallback logic: a passing test suite only proves the fixture dates you thought to write, not the real edge (here, "before recorded history begins") that interactive testing found in about a minute.

- **UI-6.6's Hindi/Telugu query-expansion glossary (`data/glossary.ts`) is built entirely from the `gloss` field already shipped on `data/answers.ts`'s q4, not new content.** Only q4 carries a `gloss` array (5 Hindi term pairs); no answer has a Telugu one, so Telugu query expansion currently does nothing beyond MiniSearch's own fuzzy/prefix matching on Telugu text against an English-only corpus (which will mostly miss). ## Phase 7

- **UI-7.1's CI e2e test (`tests/e2e/demo.spec.mjs`) is a bespoke playwright-core script, not a `@playwright/test` suite, and is `.mjs` not the D2 target structure's literal `demo.spec.ts`.** D1's approved dependency list has `playwright-core` only, and `playwright-core` alone has no test runner (no `test()`/`expect()`, no HTML reporter) — that's what the separate `@playwright/test` package provides. Rather than add a second, heavier Playwright package for one suite, this session followed the project's own already-established convention (`scripts/shots.mjs`, written the exact same way since Phase 0): a plain Node script using `playwright-core` directly, with hand-rolled `ok()`/`process.exit(1)` assertions. `.mjs` instead of `.ts` for the same reason `shots.mjs` is `.mjs`: no TypeScript-execution runtime (`tsx`/`ts-node`) is installed, and adding one just to run a script would be another undocumented new dependency. The script does real interactive-state testing that `shots.mjs`'s static per-route sweep doesn't: it loads an example Case, walks Classify → Owe → Say → Kisan mode → an unmatched Ask question (relevant-clauses fallback) → Dossier print → How it works, asserting on real rendered content (not just "no crash"), plus axe scans at three of those interactive states. `.github/workflows/ci.yml` installs a real Chrome via the `browser-actions/setup-chrome` GitHub Action (not an npm dependency) for both this script and `scripts/shots.mjs`, mirroring how this local sandbox already falls back to a fixed pre-installed Chromium path when `CHROME_PATH` isn't set.
- **UI-7.2 presenter mode's `?present=1` is read from the real, top-level browser query string (`window.location.search`, read once on mount), not through wouter's `useSearch()`.** UI-6.2's custom `src/lib/hashLocation.ts` repoints `useSearch()` at the search *inside* the hash (`#/path?search`) so per-route params like `#/ask?mode=kisan` work; `?present=1` is meant to turn presenter mode on for the whole session regardless of which route loads first (`https://.../?present=1#/case/describe` should work exactly like `?present=1#/`), which only a real top-level query read gives. A seeded demo Case ("R reset") uses `ashwaExtractExample()` (data/examples.ts): the closest existing match to FINALS-STRATEGY §12's "Meera" narrative (a startup's new-process patent potential plus real ABS duties), though her script specifically describes a 9-herb churna with a 7/9 TK-proximity overlap, which does not exist in this app's small demo plant/formulation set (data/plants.ts, data/formulations.ts, both deliberately kept small and unreviewed per UI-6.1's own content rule). Building that exact fixture would mean inventing a new, larger reference formulation, which is UI-6.5-class content this session has consistently deferred to a legal/AIIA reviewer; noting the gap here rather than fabricating a bigger demo formula to make the presenter-mode "R" key match the pitch script exactly.
- **UI-7.3 mobile QA could only be run as Chromium-based emulation, not on the real Android phone and iPhone the master plan asks for; this environment has one browser engine (a pre-installed Chromium) and no physical devices.** Ran 16 checks across four emulated profiles rather than skipping the task: (1) Android Chrome proxy (360x800, real UA, Chromium's real SpeechRecognition present) — no horizontal scroll on Home/Describe, the mic button renders, Sahayak opens as a genuine bottom sheet (not a full-screen takeover) and closes cleanly, zero console errors; (2) iOS Safari proxy (390x844, Safari UA, `window.SpeechRecognition`/`webkitSpeechRecognition` deleted via an init script to match real Safari's actual lack of the Web Speech API) — confirmed the mic button correctly disappears with no `alert()` and no broken layout, matching UI-5.4's feature-detection design, zero console errors; (3) Firefox desktop proxy (same SpeechRecognition removal, matching real Firefox's own lack of support) — mic hidden, the rest of the Ask page fully usable; (4) desktop projector width (1366x768) with presenter mode on — no horizontal scroll, `?present=1` activates correctly at that width. FINALS-STRATEGY §10's own "failure-proofing" section already calls for two people to rehearse the demo on the real laptop-plus-phone setup at least 10 times before presenting, which is the right venue to close this gap, not something achievable from this sandbox.
